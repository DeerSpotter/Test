# Codec compute route and supporting engines

## Goal and boundaries

Use fixed-function hardware for useful work while CUDA runs a separate workload. The established arithmetic route is **NVENC input → NVDEC H.264 reconstruction arithmetic → NVENC result/feedback**. The host prepares codec instructions, submits jobs, and checks results. A security engine is a possible *supporting* worker for an existing cryptographic or integrity task. It is not required to replace NVDEC's arithmetic.

| Stage | Intended job | Evidence and limit |
|---|---|---|
| Host | Prepare streams, queue work, process completions, and reconstruct bytes when needed | Preparation and output conversion remain significant CPU costs. Codec hardware has not been shown to select the next job without host orchestration. |
| NVENC | Preserve structured operands and encode computed frames for another stage | The two-input and feedback tests verified exact outputs and intermediate handoffs. |
| NVDEC | Perform supported operations during H.264 weighted prediction and reconstruction | Exact clipped additions and XOR bit-plane outputs were verified on a Tesla T4. The XOR byte-output path was much slower than direct Python XOR for its fixture. |
| Security hardware, **if accessible through a supported command** | Hash or authenticate a prepared stream, or decrypt required protected input and encrypt required output; investigate completion signaling for scheduling | The T4 Tegra driver probe did not expose this route. SEC2 firmware and the Jetson Tegra security engine are distinct interfaces. The OpenSSL XOR proof used the CPU; no GPU security execution or scheduling was established. |
| CUDA | Run the user's existing, unrelated compute job concurrently | Codec interference with a busy CUDA job and physical engine activity remain unmeasured. CUDA API use for surfaces/copies is already present; codec-internal programmable-core activity must be profiled. |

The security stage should be included only when the actual workload already needs its operation. For protected encoded input, the proposed order is **security decrypt/authenticate → NVDEC arithmetic → NVENC result → security authenticate/encrypt**. The codec cannot consume ciphertext as an ordinary H.264 stream. The first security operation is a dependency; output protection for one job may overlap codec processing of another. A hash of prepared streams could also help a reuse cache *if* hashing is cheaper than the current cache checks and a hardware implementation is available. These are designs to measure, not completed integrations. The host still connects stages and reacts to completions.

### Tandem operation and success criterion

Queue multiple independent jobs so that, after the pipeline fills, security work for one job can run while NVDEC and NVENC handle another. A serial dependency within one job still has to finish in order. The steady-state rate is limited by the slowest stage and by shared memory/transfer contention; adding another engine does not guarantee overlap. The host should submit each ready stage on completion and keep the queue bounded.

Lower latency for a single XOR result is **not** the only success criterion. Even if the codec route takes longer than a CPU calculation, it could be useful if it frees enough CPU capacity for other tasks, increases whole-system completed jobs per second, and leaves the existing CUDA workload within an acceptable performance bound. Measure these together. The first byte-output run took 2,756 ms wall time versus 11.7 ms median direct Python XOR, but did not measure total CPU time. A separate T4 run measured 4,027 ms of host-plus-child CPU time for the codec route versus 26.7 ms median direct Python XOR CPU time. The shared Colab runtime varied between runs; each comparison is confined to one run's same-runtime baseline. This small raw-input fixture currently **adds** CPU work. A separate security stage must earn its submission and transfer cost.

**Primary offload metric:** for identical raw inputs, usable outputs, and any genuinely required protection work, compute `net CPU time freed = total CPU time of direct CPU route − total CPU time of codec plus security route`. Count preparation, stream packing, process startup, FFmpeg children, transfers, synchronization, output decode/reconstruction, security submission, and host orchestration. Measure user plus system CPU time across the entire process tree without double counting. Also run a separate productive CPU task and report its completed work during the same interval. A positive isolated CPU-time difference is useful only if that capacity is actually available under concurrent load and overall throughput/CUDA performance remain acceptable.

## Custom SEC2 API feasibility

We can create an application API and, if needed, a new driver-facing adapter. The missing application API is an engineering problem, not proof that SEC2 is unusable. The Turing driver already communicates with SEC2 for defined firmware and boot duties. That establishes a host-to-SEC2 command path, **not** an available command to hash user buffers, run arithmetic, or select the next NVENC/NVDEC job. An API wrapper cannot make firmware execute a command it does not implement. Autonomous scheduling would require an appropriate SEC2 firmware command and a way to signal or submit codec work, or a separately supportable firmware/driver extension. Until demonstrated, the host remains the scheduler.

1. Inspect public driver source and the target machine's installed driver/firmware inventory for SEC2 commands, queue ownership, completion signals, permissions, and callable interfaces. Record the exact GPU and driver. Keep hardware probing read-only; do not patch the live driver or submit undocumented register commands.
2. If an existing command can accept a useful user workload, build an explicit application-to-driver adapter for that command, with bounded inputs, version checks, error reporting, and exact known-answer tests. Verify the actual execution engine, not just the API's return value. Keep Jetson `*-aes-tegra` AF_ALG names separate from T4/Blackwell SEC2 capabilities.
3. If a supported SEC2 completion or dispatch primitive exists, test a small bounded queue: job A's completion should cause the next ready NVDEC/NVENC submission while job B is in flight. Measure host CPU time, dispatch latency, exact output, backpressure, and interference with a busy CUDA workload. If the driver still submits each codec job, report this as host scheduling assisted by SEC2 signals, not autonomous SEC2 scheduling.
4. If no such command exists, document the missing firmware/driver capability and assess extension feasibility separately. A host API alone is still useful for managing codec queues, but it cannot claim SEC2 compute or GPU-side scheduling.

Public starting points: [NVIDIA's open driver SEC2 boot command call](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/src/nvidia/src/kernel/gpu/gpu.c) and [Linux Falcon firmware and secure-mode documentation](https://docs.kernel.org/gpu/nova/core/falcon.html).

## Same-device experiment

1. Run identical raw-input-to-usable-output CPU and codec routes on one device. Record wall time, total process-tree user and system CPU time, preparation, codec time, output conversion, transfers, and output hashes. Keep the comparison at the same input and output boundary.
2. Add a **required** security-side task with an optimized CPU implementation on the same input/output stream. Record codec throughput, crypto throughput, total wall and CPU time, and exact arithmetic plus cryptographic verification. If there is no real security requirement, use hashing for a measured reuse cache, including its lookup and miss costs.
3. Investigate a stock or custom application API backed by a verified security-engine driver/firmware command. Only if such a command is available, run the identical workload through that engine. Prove the selected driver/engine and account for submission, transfer, synchronization, and key-management costs. Compare it with step 2 **on the same device**. Never label OpenSSL software execution or a CPU-hosted adapter as security hardware.
4. Run the existing CUDA workload alone, then with the codec route and each supported security configuration. Run independent jobs in tandem after the pipeline fills. Record completed jobs per second, each engine's throughput, GPU engine activity, total process-tree CPU time, completed work by a separate productive CPU task, end-to-end latency, and exact results in the same measurement window. Determine whether the added stage improves whole-system throughput or frees useful CPU capacity without reducing the CUDA job unacceptably, even if an individual codec job has higher latency than direct CPU math.
5. If those tests justify it, use completion events and bounded queues to dispatch the next ready codec/security job. Measure backpressure and dispatch overhead. The engines do not become an autonomous general-purpose scheduler merely because the pipeline is connected.

The Tesla T4 supports the codec baseline, but our explicit Tegra crypto driver bind failed there. This does not prove T4 SEC2 lacks usable commands. Its accessible command set remains to be established before a hardware comparison; a custom API is one route to expose an existing capability. Results from different GPUs should be reported separately rather than combined into a speedup ratio. In the narrower already-encoded, prebuilt-stream comparison (results 09–10), NVDEC reduced measured host CPU time on an idle T4, but the concurrent CPU worker completed fewer jobs than with decode plus AVX2. That does not establish net productive CPU capacity gained from raw inputs. NVIDIA's Jetson documentation lists AES and hash engines, but also warns of substantial security-engine submission overhead for common small requests.
